# v0.19.7：把常用开发脚本收进仓库，顺手量了导出内存峰值

这一版不动程序：导出的成品、登录流程、一键升级都和 v0.19.6 一样。

## 为什么

两件小事攒在一起：

1. 发版、推送、覆盖率体检那几步一直是靠「临时目录里的脚本」在跑。它们只存在于开发机上：换台机器、或者过几个月再回来看，就得重新写一遍，而且容易忘掉上次踩过的坑（代理坏掉时 `git push` 会挂十几分钟、GitHub 的标签对象字节和本地不一样）。
2. 一直有人说大串导出「吃内存」，但从来没量过。没数据就只能猜，猜完可能白改一版实现。

## 这版做了什么

### 四个开发脚本收进 `tools/`

- `tools/push_one_commit.py`：只推本地 HEAD 一个提交，推完回读分支引用确认。代理死掉时它是唯一还能秒级完成的推送方式。
- `tools/fix_tag_object.py`：把本地的附注标签对象对齐到 GitHub 建出来的字节。GitHub 建对象时会去掉 message 结尾的换行、保留提交者的时区，本地 `git tag -a` 做不到，这个脚本穷举「时区偏移 × 结尾换行」找出命中远端 sha 的那组。
- `tools/cov_audit.py` / `tools/cov_funcs.py`：覆盖率体检。前者按文件列出未覆盖的行，后者按函数汇总——上一版补的那批用例就是靠它挑出来的。

四个脚本都改成了「按文件位置找仓库」，仓库里不留本机路径。

### 导出内存峰值（实测）

做法：造一段大串，用 `tracemalloc` 记导出过程中的峰值，和正文字节数对比（不下载图片，只看文本与拼接的开销）。

| 规模 | 正文字节 | TXT | Markdown | HTML |
|---|---|---|---|---|
| 2000 帖 × 800 字 | 4.6 MB | 12.3 MB | 8.6 MB | 14.5 MB |
| 5000 帖 × 800 字 | 11.4 MB | 30.8 MB | 21.2 MB | 35.8 MB |

倍数稳定在 2.7× / 1.9× / 3.1×，随规模线性放大。结论：**没有额外内存放大，不需要为它改实现**。HTML 最大是正常的——它要把正文拼成一份文档，图片内嵌时才会另算（base64 会把图片撑大约三分之一，那部分和图片本身大小成正比，跟帖子数无关）。

程序没变，不升级也不影响使用。想留一份带开发脚本的完整仓库，换这一版即可。
