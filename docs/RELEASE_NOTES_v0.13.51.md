# v0.13.51：给「登录读不到 userhash」做现场取证（外加修两处会误导人的诊断）

## 这一版改什么

上一版之后你复验了一次，还是读不到。我这次没有再猜，先把「本机已经排除的可能」和「这次要留下的证据」讲清楚。

1. **先排除了两条。** ①用真 Edge + 本机一个临时 HTTP 服务写的探针证明：站点用**响应头**
   `Set-Cookie: …; SameSite=None; Secure; Partitioned` 种下的分区饼干（CHIPS），程序那四条读法
   （按地址读 / 整罐读 / 存储读 / 页面 JS）**全都看得见** —— "分区饼干对程序隐身" 这条假设不成立。
   ②对账行里的「罐路径=」报的那只常驻罐（`%APPDATA%\xdao-export\browser-profile`）从 2026/10/1 起
   就再没被碰过（Cookie 库 20480 字节、里面一行都没有）：你那次真正在用的是一次性 %TEMP% 目录，
   这一行报错了罐 —— 这是要修的。
2. **把现场钉进运行日志。** 新增一行「现场：」，每隔十几秒写一次（内容没变就不重复写）：
   *上一轮花了多少秒* ＋ *这一刻浏览器里每一份罐各有哪些名字*（带分区的饼干会标出来）
   ＋ *每扇页面标签挂在哪份罐里*。这样「登录落在哪一秒、罐是不是跟着长、读循环有没有被别的
   步骤顶住」事后一眼看得出 —— 你贴回来的那三行对账几乎一模一样，恰恰缺的就是时间轴。
3. **节拍也算进去，并且慢步骤跑完再读一次。** 等待循环本该 1.5 秒读一次，可你那两次读取相隔
   十几到几十秒：怀疑是"领饼干"那几步（页面内 fetch、HTTP 重放、逐窗/逐上下文探罐）把节拍顶住了。
   现在每轮的耗时直接写进「现场：」那一行；慢步骤跑完还会**立刻再读一次**，最坏情况下的发现
   延迟从"一整个轮次"缩回"一次 CDP 往返"。
4. **提前落「读罐详单」。** 只要页面已经不是登录页（站点认为登录成了）、四条读法却还看不见
   userhash，就把详单**当场**写到 `%TEMP%`（以前要等满 300 秒才写，而你多半早就截图或取消了）。
   这份文件里有每条读法的原始返回（域、路径、分区键、哪一份罐），是唯一能逐字段比对的证据。
5. **顺手修「罐路径=」并多找一处。** 资料目录现在按浏览器进程的命令行问（`--user-data-dir=`），
   `罐=` / `罐路径=` 报的是真正在用的那只；另外页面自己的 `localStorage` / `sessionStorage` 里
   也找一次 userhash（万一站点把它放在那儿）。
