# v0.13.50：给发版脚本补一句 return（程序本身没变）

## 这一版改什么

这是一次**补丁版本**，跟你手上的用法完全无关：程序界面、导出结果、命令行开关和 v0.13.49 一模一样，
包里唯一不同的就是版本号那一串。要修的是 v0.13.49 那次重构在**发版脚本**里留下的一个真实 bug。

1. **症状。** v0.13.49 发布时 `tools/make_release.py` 崩在打印那一行：
   `TypeError: 'NoneType' object is not subscriptable`。接口其实**已经把 Release 建好了**，
   脚本却在打印时崩掉，于是**两个附件一个都没上传**（当次的两个附件是事后手动补的）。
2. **根因。** v0.13.49 把四个打包/发布脚本共用的 GitHub 问答抽成 `xdao/github_api.py` 时，
   `make_release.py` 里两个取响应体的包装函数（`request_json`、`request_text`）**漏了一句 `return**` ——
   两个函数都回 `None`，脚本自然崩。**过去所有用例都把这两个函数整个换掉**，所以那两行从来没被跑到。
3. **修法。** 两处各补 `return body`，并新增三条用例钉住它们的返回值：把最底下的
   `request_bytes` 换成「记参数 + 照对方的 `parse` 处理响应体」的假货，**不替掉** `request_json` /
   `request_text` 本身 —— 这是这次的教训：替身换得太多，等于把被测的那几行从覆盖里挖掉。
   顺手用 AST 扫了一遍「调了 `request_bytes` 却没有任何 `return` 的函数」，仓库里只有这两处。
4. **为什么还要单独发一版。** 事故只影响发版脚本（`tools/` 不在免安装包里），但被 `v0.13.49`
   这个标签指着的那份提交**带着一个坏掉的发版脚本**。按仓库规矩，仍然补一个补丁版本，
   让「最新 Release」与仓库状态一致（`tools/repo_check.py` 会核这一条）。

**登录读不到 `userhash` 的问题仍然开着**，这一版与它无关。下一步按《架构评审》§8.4 做的是
「逐扇页面目标各自读罐 + 罐指纹变化就重读 + 详单落盘」；等你下次真机复验时，
把「读罐对账」整行（以及需要的话那份「读罐详单」）贴回来。

- 全量用例 **1856 passed / 7 skipped**（收集 1863 项）；
- 契约用例（文档事实、版本号一致、使用说明分段、文本卫生、打包清单、公开材料）全绿；
