# 失败模式清理：出问题的时候，程序都做了什么

这一份不测「正常路径」，只测**出错的时候**：网络断了、接口返回垃圾、磁盘满了、
中途取消、图片全挂、浏览器找不到、配置写坏了、串号打错。每一格都是一个真实
执行过的输入，记录三件事——程序怎么反应、用户看到什么、有没有留下垃圾。

范围：`xdao` 包与 `main.py` 的现有行为，只读调用，不改任何源码。
复现脚本是一次性的（`failmode_probe.py`），跑在 `%TEMP%` 下的临时目录里，跑完自清理。

## 一、总览

| 场景 | 程序反应 | 用户看到什么 | 残留 | 风险 |
|---|---|---|---|---|
| 单页请求超时／拒绝连接／DNS 失败 | 抛 `XdaoError`，整趟导出中止 | 中文提示 + 原始 URL | 缓存里有已抓的孤儿页 | 中 |
| HTTP 5xx / 4xx | 抛 `XdaoError`，附服务端正文 | 「请求失败 500: …」+ 正文 | 同上 | 中 |
| 被限流（429） | 抛 `XdaoError`，不含 URL | 「请求过于频繁…把请求间隔调大」 | 无 | 低 |
| 接口返回 HTML 而非 JSON | 两个 API 前缀各试一遍后抛错 | 「接口返回了非 JSON 内容」 | 无 | 低 |
| 缓存状态文件损坏 | 静默回默认值 | 无提示 | 原文件被覆盖 | 低 |
| 导出目录建不出来 | 抛 `OutputDirNotWritable` | 「导出目录无法创建」+ 原因 + 建议 | 无 | 低 |
| 磁盘写满 | 抛 `OSError`，`.part` 被回收 | 「[Errno 28] No space left on device」 | 无 | 低 |
| 导出中途取消 | 抛 `ExportCancelled`，`.part` 被回收 | 日志「导出已取消」 | 无 | 低 |
| 图片全部下载失败 | 导出照常成功，保留原链接 | 逐条前 10 张 + 汇总句 | 无 | 中 |
| PDF 浏览器找不到 | **静默降级成 HTML** | 两句说明日志 | 产物变成 `.html` | 中 |
| 配置文件损坏 | 静默回默认，不备份 | 无提示 | 原配置被下一次保存覆盖 | 中 |
| 串号写成 `abc` | 全部丢弃，`return 0` | 「没有要导出的串」 | 无 | 中 |
| 串号写成 `12345abc` | 截成 `12345`，去抓不存在的串 | 抓取失败的报错 | 无 | 中 |
| 串号写成 `0` | 被当作合法串号 0 | 抓取失败的报错 | 无 | 低 |

「风险」按「用户会不会困惑」判：会静默降级、会静默丢数据、会给成功退出码的记中。

## 二、网络层

用真实的 `XdaoClient._request` 配上假的 opener，逐个注入故障。

| 注入的故障 | 实际抛出的异常与文案 |
|---|---|
| 超时 | `XdaoError: 请求超时（20 秒）：<url>` |
| 连接被拒 | `XdaoError: 网络错误：<urlopen error [Errno 10061] 拒绝连接>（<url>）` |
| DNS 失败 | `XdaoError: 网络错误：<urlopen error getaddrinfo failed>（<url>）` |
| HTTP 500 | `XdaoError: 请求失败 500: <url>` + 换行 + 响应体原文 |
| HTTP 404 | 同上，正文来自服务端 |
| HTTP 429 | `XdaoError: 请求过于频繁，已被服务器限流（429）。请稍后重试，或在设置里把「请求间隔」调大。` |
| 返回 HTML 而非 JSON | `XdaoError: 接口返回了非 JSON 内容：<url>` |

两点观察：

1. **4xx/5xx 会把响应体原样拼进错误消息**。服务端返回一坨 HTML 时，用户看到的
   就是一坨 HTML。可读性一般，但至少没有把响应体吞掉。
2. **429 那条不带 URL**。串多了以后很难判断是哪一页触发的限流。

接口返回 HTML 的那一例还暴露了一个行为：`_api_get_json` 会在**两个 API 前缀上
各试一遍**，实测请求序列是 `getCDNPath → thread?… → getCDNPath → thread?…`，
一共四个请求，比正常路径多一倍。这是设计好的重探，不是 bug，但失败时的请求量
值得知道。

## 三、抓取层

### 3.1 某一页抛异常，会中断整趟抓取

`_process_page` 直接调用 `self._client.fetch_thread_page(thread_id, page)`，
外面没有包 `try`。`_request` 的重试耗完之后抛 `XdaoError`，异常一路穿出 `fetch()`，
整趟导出失败。

代码注释里写的是「抓不下来的页先记进重试队列，不再当场 break」—— 那句话只对
**软失败**成立：client 返回 `str`、或返回的 dict 里 `success=False` 时，这一页
记进 `failed` 集合，主循环跳过它继续抓后面的页，第一遍跑完再统一补抓。**真异常
不在这套机制里**。

### 3.2 中断之后，已抓的页不会被复用

实测第 3 页抛异常后：`pages/50000001/1.json` 与 `2.json` 都在，但
`threads/50000001.json` 不存在（状态文件只在整趟成功时写）。下一次重跑时
`reason=首次抓取`、`pages_fetched=2, pages_reused=0`，请求序列仍然是 `[1, 2, 3]`
—— 已经抓好并存盘的两页被重新请求了一遍。

对长串来说，这意味着一趟跑到 70 页断掉，下次仍然要从第 1 页开始请求。这是本份
报告里最值得改的一条（见建议 1）。

### 3.3 缺页与撞上限的提示是分开的

`_assemble` 里根据 `missing` 与 `capped` 两个条件拼不同的说明：缺页时说「第 X、Y
页补抓 N 次仍未成功（最近一次失败原因：…）：这份产物只到第 M 页，缺页后面的
内容不会出现在成品里」，并明确告诉用户「再导一次通常就能补齐，已经抓下来的页
都存进缓存了」；撞页数上限时说的是「这次只抓到第 M 页（这次要抓的范围比这长）」。
两者都会把 `truncated` 置真，界面据此弹「有串没抓全」。

### 3.4 缓存目录写不进去时自动换目录

不失败。实测回退到 `%LOCALAPPDATA%\xdao-export\.cache`，抓取照常完成，并给那句
「缓存目录 <原路径> 写不进去，本次改用 <回退目录>。想固定下来可以在设置里改
「缓存目录」。」

## 四、写盘层

| 注入 | 结果 | 残留 |
|---|---|---|
| 导出目录的父路径是个文件 | `OutputDirNotWritable: 导出目录无法创建：…` + 换行 + 系统原因 + 「请换一个可写的目录，或检查该位置的权限。」 | 无 |
| 探针文件写不进去、但目录本身能写 | **不拦导出**，只少一层预警（v0.5.0 的决定，注释里写了原因） | 无 |
| HTML 写到一半磁盘满（`OSError(28)`） | `OSError: [Errno 28] No space left on device` 上抛 | 无（`.part` 被 `finally` 收掉） |
| TXT 写到一半磁盘满 | 同上 | 无 |
| HTML 写到一半被取消 | `ExportCancelled: 导出已取消` | 无 |

写盘失败的处理在五个导出器之间是一致的：`.part` 一定回收，异常一定上抛，不会
留半份成品，也不会把失败说成成功。

（注：本项最初的探针把 `OSError` 打桩打在 `Path.write_bytes` 上，而 HTML 走的是
`open()`，于是得到了「HTML 吞错误」的错误结论。改成打在 `builtins.open` 后重测，
结论是上抛 + 无残留。）

## 五、图片层

| 场景 | 结果 |
|---|---|
| 1 张图下载失败 | 导出成功（2,690 字节），日志「图片下载失败，已保留链接：<url>」，正文保留原链接 |
| 15 张图全失败 | 导出成功（8,536 字节），日志 28 行：逐条只列前 10 张，末尾「一共 15 张图片没下到，已保留原链接（逐条日志只列了前 10 张）；前三张是：…」 |
| 缺图清单落盘 | `导出报告-<日期>-<时间>.txt`，含时间、导出目录、「这次有 1 个串没能完整导出」、每个串的标题与成品名 |

单图失败会逐条说，超过 10 张才汇总 —— 这个设计是对的：少量失败能一眼看到是哪张，
大量失败则不该刷屏。缺图清单只在真有问题时写，文件名带时间戳，不会互相覆盖。

## 六、PDF 层

浏览器路径指向一个不存在的程序时：

```
正在整理 HTML…
PDF 渲染失败，改为保存 HTML（可在浏览器里打印成 PDF）…
PDF 渲染失败，已改存 <name>.html；在浏览器里打开它，按 Ctrl+P 选「另存为 PDF」即可得到同样的结果。
```

`save()` 返回的是 `.html` 的路径，不抛异常。`fallback_html` 默认开着，
CLI 会把这段说明以「说明：」打印出来。

这是有意的兜底（找不到浏览器不等于用户不需要内容），但**它是静默的降级**：
用户要的是 PDF，拿到的是 HTML，只在日志里说了一声。如果用户没看日志，会以为
导出失败或者找不到文件。建议保留兜底，但把「这次没有 PDF，只有 HTML」提到
更高的可见度（见建议 4）。

## 七、配置层

| 场景 | 结果 |
|---|---|
| `config.json` 内容损坏 | 静默回默认（`timeout=20.0`、`page_workers=2`），不报错、不备份原文件 |
| `timeout` 是 `"abc"` | 回默认 |
| `page_workers` 是 `99` | 夹到上限 |
| 保存失败（目录不可写） | `save()` 返回 `False`，界面据此提示（v0.13.53 起） |

最需要留意的是第一条：配置坏了会静默丢弃，并且下一次保存就把原文件覆盖掉。
用户不会知道自己的登录饼干、导出目录、监控列表是「被重置了」还是「本来就没设」。

## 八、输入解析

`parse_thread_id` 的几个边界：

| 输入 | 返回 | 备注 |
|---|---|---|
| `""` / `"abc"` / `"/t/"` / `"-5"` / `True` | `None` | 正确 |
| `"0"` | `0` | 没有 `> 0` 校验 |
| `"12345abc"` | `12345` | 正则前缀匹配 |

后两个会让程序去抓一个不存在的串，报的是抓取失败而不是「串号写错了」。

更值得注意的是退出码：`main.py abc` 会打印「串号截止把列表里的串全都挡住了，
没有要导出的串。…」然后 **`return 0`**。也就是说，参数写错、一个串都没导，
退出码却是成功。脚本里靠退出码判断结果的人会踩到。

`main.py` 的退出码约定：参数错误 `2`、`XdaoError` `1`、`KeyboardInterrupt` `130`、
「列表被截止挡光」`0`、自检按失败项数 `1/0`。

## 九、界面、监控与升级

- **单个串失败不拖垮整批**：导出 worker 对每个串分三档处理——取消、`XdaoError`、
  其它异常；最后按「取消／有失败／只有缺页／全好」四种情况弹不同的对话框，文案
  里带「已经导出的文件在：…」「可以点「重试失败项」」这类下一步指引。
- **`PermissionError` 有专门的解释**：把三类成因（从受限目录启动、受控文件夹访问、
  未签名被安全软件拦）都列出来，并给出 `%LOCALAPPDATA%\xdao-export\导出` 这个兜底位置。
- **监控循环不会因为一个串出错而停**：`check_once` 内部已经收掉 `XdaoError` 与其它
  异常，只把 `state` 置成「出错」并记 `last_error`；通知回调与通知本身都各自吞异常。
- **升级检查不抛异常**：五种失败都转成 `UpdateResult(ok=False, reason=…)`，
  文案分别是「接口返回 <code>」「连不上 GitHub（…）」「接口返回的不是 JSON」
  「接口返回的结构看不懂」「接口里没有版本号」。

## 十、建议

1. **让已抓的页在中断后能被复用**（中）：整趟失败时不写状态文件，导致下一次
   `pages_reused=0`。可以考虑每次成功落盘一页就更新一个轻量进度文件，或让
   `load()` 在没有状态文件时按 `pages/<id>/*.json` 的实际存在情况认账。
2. **单页异常不该中断整趟**（中）：给 `_process_page` 的那次 `fetch_thread_page`
   包一层，走和软失败相同的「记进 `failed`、稍后统一补抓」路径。注释里描述的
   行为本来就该是这样。
3. **串号写错时报「串号写错」**（中）：`parse_thread_id("0")` 与
   `parse_thread_id("12345abc")` 都该返回 `None`；`main.py` 在「一个串都没导出」
   时退出码不该是 0。
4. **PDF 降级要在收尾时说出来**（中）：日志有两句，但对话框/退出码层面看不出来。
   建议在「完成」提示里加一句「其中 N 个是 HTML（浏览器不可用）」。
5. **配置损坏时备份原文件**（低）：坏配置重命名成 `config.json.bad`，用户下次还能
   找回自己的设置；同时日志里说一句「配置读不出来，已改用默认值」。
6. **429 的错误消息补上 URL 或页号**（低）：限流时最需要知道的是「哪一页」。

## 十一、不在这一项的范围里

- 不做真实断网/断电源/磁盘满的物理实验，只做进程内的故障注入。
- 不评价网络层重试次数的合理性（那是「爱惜站点」的既定约束：间隔 0.08 秒、
  重试 2 次、遵守 `Retry-After`），只记录失败时的表现。
- 不改任何源码；上面六条建议都是描述，不是改动。
