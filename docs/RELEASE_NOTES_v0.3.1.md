## 本次更新

v0.3.0 引入了 PDF 导出，但**打包版无法使用**。这一版把它查清楚了，并让程序优雅降级。

### 打包版导出 PDF 会失败（已查明原因，但无法绕过）

**现象**：用 Releases 里的免安装包执行 `-f pdf`，浏览器子进程返回
`2147483651`（`0x80000003`，STATUS_BREAKPOINT），PDF 生成不了。

**排查过程**（每一条都实测过）：

| 假设 | 结果 |
|---|---|
| 打包版把 Tcl/Tk 路径塞进环境变量，浏览器加载到版本不匹配的 DLL | 去掉后仍失败 |
| 继承的环境变量有问题 | 传干净环境仍失败 |
| 工作目录在打包目录，DLL 搜索命中了打包的运行库 | 换干净工作目录仍失败 |
| 管道捕获输出造成句柄继承问题 | 改成重定向到文件仍失败 |
| 进程树问题 | 经 `cmd.exe` 代启仍失败 |
| 句柄继承问题（彻底排除） | 用 ctypes 直接 `CreateProcessW`（无句柄继承）仍失败 |
| Chrome 本身有问题 | **从命令行用完全相同的参数启动，正常生成 PDF** |

**结论**：从 PyInstaller 冻结进程创建浏览器子进程时，Chrome 会在启动阶段被系统中断，
属于打包运行时的系统级限制，本项目无法绕过。

### 现在会怎么做

打包版遇到这种情况**不再只是报错**：

- 自动把内容存成 **HTML**（图片已内嵌），并在日志与界面里提示
  「在浏览器里打开它，按 Ctrl+P 选『另存为 PDF』即可得到同样的结果」；
- 错误信息里会带上 `STATUS_BREAKPOINT` 与原因说明，便于以后排查；
- 需要真正的 PDF 时，从源码运行即可：

  ```powershell
  python main.py 67024789 -f pdf -o D:\备份
  ```

源码运行的 PDF 导出**完全正常**（实测 33 页 / 626 楼 → 408 页 / 157.9 MB，字体内嵌）。

### 其它

- 新增隐藏开关 `--pdfdiag`，用于诊断打包版为何启动不了浏览器；
- 测试从 213 项增至 **218 项**，覆盖降级路径与错误提示。
